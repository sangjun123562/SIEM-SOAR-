# 가상 기관 로그인 — 보안관제 시연용

사용자 요청(2026-11-18)으로 구매 신청·승인·반려 업무를 제거했다.
계정 선택 → 정상/실패 인증 → 세션 확인 → 로그아웃만 제공한다.
이 변경은 초기 구매 업무 범위를 줄이는 합의된 범위 변경이다.

## API
- GET /: 기관 통합 로그인 화면
- POST /api/login: 기존 계정·비밀번호 검증과 로그인 감사 기록
- GET /api/session: 현재 인증 정보, 미인증 401
- POST /api/logout: 세션 해제와 로그아웃 기록
- 구매·품목·결재 API는 제거되어 404다.
- GET /api/documents: 자료실 목록. 로그인한 계정이 열 수 있는 문서만 보인다(미인증 401)
- GET /api/documents/<id>: 문서 열람. 성공·거부(403)·없음(404)·미인증(401) 모두 `document_read` 로그를 남긴다
- GET·POST /api/access-requests, POST /api/access-requests/<id>/approve · reject · revoke: 열람 권한 요청·승인·반려·회수(문서 소속 부서 팀장). 회수·반려·승인·거부 시도 모두 `access_request_*` 로그를 남긴다

## 자료실 (2026-11-22 추가, 사용자 지시)
구매 업무 제거와는 별개로 부서·등급에 따른 문서 열람 권한을 시연하기 위해 추가했다. 구매·결재 동작은 여전히 없다.
- 부서(DB 값 → 화면 이름): 영업 → 행정지원과, 인사 → 인사총무과, 보안 → 정보보안과
- 계정: alice(영업 사원), bob(영업 팀장), carol(보안 사원, 개발에서 변경), dave(인사 팀장), erin(인사 사원), frank(보안 팀장)
- 등급: 일반(로그인한 모두), 부서(같은 부서), 기밀(같은 부서 팀장만). 보안팀도 다른 부서 문서에는 예외가 없다
- 권한 규칙은 `documents.py`에 있고 `tests/test_erp_documents_access.py`가 DB 없이 시험한다
- 문서는 업무 절차 안내 위주이며 통계·수치는 넣지 않는다

## 데이터와 증거 보존
ERP PostgreSQL 사용자와 기존 구매 테이블/행은 삭제·초기화하지 않았다.
과거 purchase_* 관제 로그와 원본 raw_id 계약도 그대로 보존한다.
새로운 구매·결재 동작은 제공하거나 기록하지 않는다.

## 화면과 인증
입력형 텍스트 필드 없이 계정을 선택한다. localhost 시연 연결 프로그램이
해당 테스트 계정의 인증값을 메모리에서 공급하며 실제 서버의 비밀번호 검증은 유지한다.
인증값은 저장소 HTML·로그에 넣지 않는다. 직접 Caddy 주소에서는 인증값 공급 없이
계정 선택만으로 로그인되지 않는다. 보안 시연 도구의 실패 유형은 클릭당 1회만 전송한다.
화면 부서 표시는 영업→행정지원과, 개발→디지털정보과이며 DB 코드는 유지한다.

## 로그인 후 업무 홈
정상 인증 후에는 로그인 화면과 분리된 기관 포털로 전환한다.
업무 홈·내 계정·이용 안내 메뉴와 세션 확인·로그아웃을 제공한다.
계정·소속·역할은 기존 인증 API 응답을 사용한다. 확인 시각은 응답을 받은 브라우저 시각이다.
세션 확인 실패 시 마지막 계정 정보는 남기되 상태를 확인 불가로 표시하고,
401 응답 또는 로그아웃 후에는 로그인 화면으로 돌아가 표시된 계정 정보를 지운다.
구매 업무·가짜 통계·보안 경보를 추가하지 않는다. 관제 앱과 별개의 ERP 접속 후 화면이다.

## 자료실 보강 기록 (2026-11-22, 제작 단위 4개)
보안실무자의 구조 검토 지적을 방어전의 접속 승인 구조(요청 → 승인(만료) → 회수, 매 요청 재검사, 기록을 덮어쓰지 않음)에 맞춰 단위별로 고쳤다.

| 단위 | 바꾼 것 | 정상 요청 | 거부되어야 할 요청 |
|---|---|---|---|
| 1. 대시보드 `/refresh` | 분석가가 상태 조회로 DB 상태를 바꾸지 못하게 승인 권한 요구(`src/soc/dashboard.py`) | 승인자 200 | 분석가 403 |
| 2. 매 요청 재검사 | ERP가 부서·직급을 쿠키가 아니라 매 요청마다 DB에서 읽음. DB 오류 시 로그인하지 않은 것으로 봄 | 복구 후 팀장 승인 200 | 강등된 팀장의 기존 세션으로 승인 403 |
| 3. 회수·중복 방지 | `revoked` 상태, 팀장의 즉시 회수 API, 열린 요청 중복 방지 유일 인덱스 | 팀장 회수 200 | 다른 부서 팀장·본인·사원 회수 403, 비로그인 401, 이미 회수 409, 동시 6건 중 1건만 201 |
| 4. 감사 로그 | 승인 로그에 `expires_at`, 반려 사유, `access_request_revoked` 이벤트. 기록을 먼저 남기고 커밋 | 로그 4종 확인 | — |

**검증:** 실제 ERP(18888 입구 경유)에서 29개 확인 통과, 동시 요청은 ERP 컨테이너 안에서 직접 6건 전송. Python 74건 OK(1 skip), Node 6건 OK, 대시보드는 실제 로그인으로 `analyst1` `/refresh` 403 확인.
**DB 오류 경로(실제 실행):** ERP DB 컨테이너를 멈추고 ERP 안에서 직접 호출 — 문서 열람·목록·세션·요청 목록·승인 시도가 모두 401(데이터를 돌려준 요청 0건, 약 5초 안에 응답), 재로그인은 503(로그인 실패로 기록하지 않음). DB 복구 후 같은 세션이 다시 정상. 연결 제한 시간 3초(`connect_timeout`).
**코드 정리(보안실무자 수행, 동작 불변):** 요청당 DB 연결 2회 → 1회, 반복된 Origin 검사·401/403/404 응답·audit 메타·SELECT를 헬퍼로 통합, 세션 쿠키에는 `uid`만 저장(부서·직급은 DB에서 읽음), 화면 JS의 중복 정리. 재검증: 시나리오 58건 통과.
**미실행:** 브라우저에서 회수·반려 사유 입력 화면을 직접 누르는 시험. DB를 멈출 때 Docker 네트워크가 흔들려 18888 입구가 잠깐 502를 내는 것은 입구 경로의 시험 환경 문제로 보이며 ERP 로그에는 오류가 없었다(원인 단정 안 함).

**알려진 한계(이번 범위 밖):**
- 부서마다 팀장이 1명이라 부재 시 승인자가 없다. 팀장끼리 서로의 기밀 문서를 승인해 주는 담합은 막지 않는다(요청자 ≠ 승인자만 검사).
- ERP 계정과 대시보드 계정은 별개다. 보안 부서 인원이 관제 역할을 맡는 매핑은 문서로만 정한다.
- 만료는 로그 줄이 남지 않는다(승인 로그의 `expires_at`으로 계산). 로그아웃은 쿠키 삭제뿐이지만 매 요청 DB 재검사로 권한 변경은 바로 반영된다.
- 목록은 열 수 없는 문서의 제목을 숨기지만, 열람 요청 목록(`/api/documents/restricted`)은 요청에 필요해서 제목·부서·등급을 보여 준다(본문 없음).
- 문서 번호가 제목에서 만든 고정 UUID라 저장소를 본 사람은 계산할 수 있고, 403/404 차이로 존재 여부가 드러난다.
- 탐지 룰은 같은 문서를 반복해서 거부당해도 센다(서로 다른 문서 수가 아니라 건수 기준). 해제한 사람의 기록(대시보드)은 남지 않는다.
