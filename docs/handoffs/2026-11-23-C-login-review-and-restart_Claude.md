## 변경 결과

**로그인 주의 사건 2종 (`src/soc/detector.py`, `incident_service.py`, `dashboard.py`)**

| 규칙 ID | 조건 (같은 계정명·같은 수집 방식·신뢰 IP·5분 안) | 화면 표시 |
|---|---|---|
| `RULE-ERP-LOGIN-SUCCESS-AFTER-FAILURES-001` | 같은 IP에서 인증 실패(401) 3~4회 뒤 로그인 성공 | 주의 · 인증 성공 확인 필요 |
| `RULE-ERP-LOGIN-SUCCESS-FROM-DIFFERENT-IP-001` | 한 IP에서 실패 3~4회 뒤 다른 IP에서 성공 | 주의 · 실패와 성공의 출발지가 다름 |

- 두 사건 모두 `medium`이고 조사용이다. `block_rule_eligible=False`라서 화면과 서버(`request_human_approval`) 양쪽에서 차단 승인을 거부한다.
- 실패 5회로 이미 반복 실패 경보에 쓰인 실패는 주의 사건 근거로 다시 쓰지 않는다. 기존 사건에서 확인한다.
- 근거에는 실패와 성공을 모두 넣고, dedup 키는 성공 기록 번호를 쓴다. 같은 로그를 다시 읽어도 사건은 1건이다.
- 사건 상세·미리보기 근거 표에 "결과"(성공/실패) 칸을 추가했다. 새 대시보드 상세 표 머리글도 같은 칸 수로 맞췄다.

**수집기 재시작 분류 (`src/soc/collector.py`, `live_collector.py`)**

- 수집기를 켤 때 파일별로 파일 번호(inode)와 크기를 기억한다. 첫 읽기부터 줄마다 분류한다.
  - 시작할 때 있던 파일: 그 크기 앞에서 시작한 줄은 `replay`, 뒤는 `live`다. 시작 전에 쓰다 만 줄은 나중에 완성돼도 `replay`다.
  - 시작할 때 없던 파일(새 설치 직후 첫 로그인 전의 `erp.jsonl` 등)이나 시작 뒤 교체된 새 파일: 모든 줄이 `live`다.
  - 시작할 때 권한 문제 등으로 상태를 확인하지 못함: 처음 읽은 위치까지 `replay`다.
  - 수집기가 꺼진 동안 교체된 옛 파일(`.1`)의 남은 줄: `replay`다.
- 연습 초기화가 취소되면 시작 기준을 유지하고, 성공했을 때만 비운다.
- `--once`는 전부 `replay`다.
- 수집기 로그 `pass=N mode=...` 형식을 유지했다. `testbed/scripts/setup_all.sh`의 `mode=replay` 확인이 그대로 통과한다.

## 미확인 · 남은 한계

- 팀 Docker·PostgreSQL 실환경에서 주의 사건 화면, 승인 거부, 실제 수집기 재시작은 확인하지 않았다.
- 기기·네트워크를 바꾼 정상 사용자 사례에서 주의 사건이 몇 건 생기는지는 측정하지 않았다.
- PR 전 main에도 있던 수집기 한계(이번 변경과 무관):
  - 두 번 읽는 사이에 파일이 두 번 이상 교체되면 옛 파일의 남은 줄을 놓칠 수 있다.
  - 한 번도 읽지 않은 새 DB에서 시작 직후 교체되면 교체 전 파일을 읽지 않는다.
  - 꺼진 동안 교체되고 새 로그가 아직 없으면, 옛 파일의 남은 줄은 다음 로그가 쓰일 때 읽는다.
