# 관제 감사·수집 시간 보호 인수 기록

- 기준: `eldi`의 `f75ab53` 이후 검토 발견 1·2·3·5 수정. 공유 계정 정책과 성능 구조는 이번 변경에서 다루지 않는다.
- 담당: A 요청에 따른 관제 공통 코드 보강. B 소유 수집·DB·화면 영향이 있으므로 아래 적용 사항을 확인한다.

## 변경과 적용

1. 장기 차단 확인창의 JavaScript 문자열 개행 오류를 수정했다. 생성 HTML의 전체 inline script 파싱 및 1,440/1,441분 경계를 시험한다.
2. 탐지의 앵커·원본·이벤트 조회에 회차별 동일한 UTC 미래 상한을 적용한다. 원본 시각과 수집 모드는 바꾸지 않는다. 오래된 replay를 보존하며, 시간이 도달한 보류 이벤트는 새 파일 입력 없이도 다시 검사한다. 기존 24시간 범위 밖의 지연 로그 자동 분석과 호스트 시계 보정은 범위 밖이다.
3. 해제 담당자·사유·요청 시각·결과를 `action_release_audit`에 별도 저장한다. 호출 전 요청 저장, 중복 요청 차단, 통신 유실의 결과 미확인, 후속 조회의 별도 관측 상태를 구분한다. 최초 승인자와 과거 이력은 추정하여 바꾸지 않는다.
4. 깨진 로그는 `collector_errors`에 출처·파일 세대/inode·위치·길이·해시·고정 오류 종류·수집 모드·수집 시각만 기록한다. 원문과 예외 메시지는 보관하지 않는다. 오류 메타데이터와 정상 이벤트·읽기 위치는 같은 트랜잭션으로 저장한다.

- 사건 상세: 최근 해제 감사 50건. 각 로그 소스: 오류 총건수와 최근 10건.
- 해제 POST 클라이언트는 `reason`을 보내야 한다. 화면은 매번 새 `operation_id`를 발급한다. 번호 없는 구형 호출은 사건·승인·담당자·사유로 재시도 번호를 계산하므로, 실패 후 새 시도에는 새 번호를 사용한다.
- 새 DB: `db/init/002_review_audit.sql`. 기존 DB: 애플리케이션 시작 시 동일한 추가 표를 초기화한다. 기존 볼륨을 초기화할 필요는 없다. 초기화 권한이 없는 운영 계정은 DBA가 먼저 SQL을 적용해야 한다. PostgreSQL 동시 초기화는 자문 잠금으로 직렬화한다.
- 연습 초기화는 수집 오류 메타데이터를 함께 초기화한다. 해제 감사 표는 보존한다. 게이트웨이 API·네트워크·ERP DB 계약은 불변이다.

## 검증

- `python -B -m unittest discover -s tests`: 174건 중 167통과, 환경 의존 7건 건너뜀, 종료 0.
- `bash -n testbed/scripts/verify_day5_e2e.sh`: 종료 0. `git diff --check`: 종료 0.
- SQLite·가짜 조치 API: 요청 선저장/담당자 위조 무시/사유 누락 거부/중복 호출 방지/통신 유실/오류 원문 비저장/동일 트랜잭션 롤백/회전 파일 추적/화면 이스케이프 확인.
- 실제 PostgreSQL: 세션 임시 표에서 해제 선저장·완료, 오류와 offset 롤백, 원문 비저장 확인. 이 시험에서 영구 데이터 행을 변경하지 않았다.
- Docker: 대시보드·수집기 재빌드 및 기존 볼륨에서 두 표의 추가 초기화 완료. 기존 DB·ERP·게이트웨이는 재생성하지 않았다.
- 실제 인증 화면: ERP/게이트웨이 로그의 오류 표, 사건 해제 감사 표, 보고서 페이지 HTTP 200 확인. 앞선 확인창·팝업·자동갱신 동작도 검증했다.

## 미검증

실제 방화벽 차단→해제→복구 E2E, 장기 부하, DB 장애 복구는 이번에 실행하지 않았다. 가짜 조치 API/임시 표 시험을 실제 차단 성공으로 해석하지 않는다. 다음 통합 시험에서는 최신 화면의 해제 사유 입력과 이력을 함께 확인한다.
