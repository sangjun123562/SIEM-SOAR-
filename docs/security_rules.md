# 차단·잠금·승인 기준 (한 장 요약)

작성: A (2026-11-26). 기준은 코드(`erp/`, `src/soc/detector.py`, `incident_service.py`)와 팀 논의다.
**구현됨**과 **결정만 함(미구현)**을 구분한다. 미구현을 구현된 것처럼 읽지 않는다.

## 1. 한 줄 원칙

- **IP**는 보안팀이 사람이 확인하고 직접 차단·허용한다. 자동으로 막지 않는다.
- **계정**은 조건을 넘으면 ERP가 자동으로 잠그고, **풀 때는 반드시 대시보드에서 보안팀**이 푼다.
- ERP 화면 안에는 권한 요청·승인 칸이 없다. 권한 밖 문서는 막고 기록만 남긴다. 임시 권한은 대시보드에서 준다.

## 2. 누가 무엇을 하나

| 대상 | 자동으로 하는 일 | 사람(보안팀)이 하는 일 | 상태 |
|---|---|---|---|
| 로그인 계정 | 5분 안에 5회 실패하면 ERP가 10분 잠금 | 대시보드에서 해제(잠금 사건에 연결됨). 수동 잠금은 최대 24시간(1,440분) | 구현됨 |
| 승인된 IP (client-A, client-B) | 그대로 접속 허용 | — | 구현됨 |
| 비인가 IP (client-X) | ERP가 로그인 전에 거부하고 기록 | 대시보드에서 일정 시간(최대 5분) 임시 승인 | 구현됨 (ERP가 판정, 합의 완료) |
| IP 차단 | 없음 | 사건 승인 후 게이트웨이가 시험 단말만 차단(최대 30일/43,200분), 해제 후 복구. **한 단말에는 활성 차단 한 건만**(두 번째는 거절). 하루(1,440분) 넘게 차단하면 확인 창 | 구현됨 |
| 문서 열람 | 권한 없으면 403 + `document_read` 실패 기록 | 대시보드 "권한" 화면에서 기간 지정 임시 권한 부여·회수(최대 24시간) | 구현됨 |

## 3. 로그인 실패 단계 (같은 계정·같은 IP 기준 연쇄)

| 단계 | 조건 | 결과 | 규칙 ID | 차단 승인 |
|---|---|---|---|---|
| 관찰 | 실패 3회 | 의심 사건 표시 | `RULE-ERP-LOGIN-THREE-FAILURES-001` | 불가(조사용) |
| 차단 후보 | 실패 5회(같은 계정·IP, 5분) | 경보 + 사건, 사람이 승인하면 IP 차단 | `RULE-ERP-LOGIN-BRUTE-001` | **가능** |
| 같은 IP 여러 계정 | 한 IP가 서로 다른 계정으로 실패 합산 | 사건(차단 후보) | `RULE-ERP-LOGIN-IP-TOTAL-001` | **가능** |
| 계정 잠금 | 같은 계정 실패 합계 5회(IP 합산, 5분) | ERP가 계정 10분 잠금 | `RULE-ERP-LOGIN-AUTO-LOCK-001` | 잠금 해제만 가능 |
| 비인가 IP 시도 | X 단말이 로그인 시도 | 거부 + 사건 | `RULE-ERP-LOGIN-SOURCE-DENIED-001` | 임시 IP 승인 |
| 실패 뒤 성공 | 실패 3~4회 후 성공 / 다른 IP 성공 | 주의 사건 | `...SUCCESS-AFTER-FAILURES-001`, `...SUCCESS-FROM-DIFFERENT-IP-001` | 불가(조사용) |
| 여러 계정·여러 출발지 | 한 IP 다계정 / 한 계정 다 IP | 조사용 사건 | `...MULTI-ACCOUNT-001`, `...MULTI-SOURCE-001` | 불가(조사용) |
| 문서 열람 거부 반복 | 같은 계정·IP가 5분 안에 3회 거부 | 조사용 사건 | `RULE-ERP-DOC-DENIED-001` | 불가(조사용) |

"조사용·차단 불가"는 사람이 보고 판단하는 사건이다. 차단 승인 버튼이 열리는 것은 `block_rule_eligible`인 두 규칙(BRUTE, IP-TOTAL)뿐이다.

## 4. 정해진 것과 아직 정할 것

**정해짐**
- 한 PC에서 서로 다른 계정이 섞여 실패하면 정상 흐름이 아니므로 의심으로 본다. 우리 구조에는 공인 IP 개념이 없어 각 IP를 각자의 출발지로 본다.
- 계정 잠금은 자동, 해제는 대시보드(보안팀). ERP 안에서 스스로 해제하는 길은 두지 않는다.
- IP 차단은 사람이 승인한다. 합성·파일 재생·미신뢰 이벤트로는 차단하지 않는다(라이브 + 신뢰 IP + 사람 승인).

**팀 합의 완료 (2026-11-26)**
1. 단계는 **3회 실패 = 의심, 5회 실패 = 차단(계정은 자동 잠금, IP는 사람이 승인)**으로 한다.
2. "한 IP가 여러 계정에 실패"와 "한 계정 5회 실패"는 **같은 공격 흐름**으로 본다. 화면에서도 따로 심각도를 나누지 않는다.
3. 비인가 IP(client-X)는 **ERP가 막는다.** 게이트웨이에서 기본 차단하면 ERP 접속 자체가 오류(404 등)로 보여 시험환경을 다시 만들기 어려우므로 채택하지 않는다.
4. 자동 잠금은 **10분**. 시연은 "자동 잠금까지 보여주고 → 대시보드에서 수동 해제"하는 순서로 설명한다.

**팀 결정 (2026-11-27)**
- 한 시험 단말에는 활성 IP 차단을 **한 건만** 허용한다. 두 번째 승인은 게이트웨이가 `409 target_already_blocked`로 거절한다(대시보드도 같은 IP의 중복 승인을 거절).
- IP 차단 최대 시간은 대면 합의대로 **30일(43,200분)을 그대로 둔다.** 다만 1,440분을 넘는 값을 제출하면 "정말 n일 막을까요?" 확인 창을 거친다.
- 계정 수동 잠금은 IP 차단과 따로 **최대 24시간**으로 제한한다(직원 업무가 막히는 조치라서).
- 영구 차단은 **만들지 않는다.** 해제를 잊으면 단말이 영구히 막힐 수 있고, 시연에는 30일 상한으로 충분하며, 시험망 규칙상 장기 차단은 항상 해제 경로가 있어야 하기 때문이다.
- 기간 없이 로그를 내려받으면 최근 7일만 포함한다. CSV는 탭·줄바꿈으로 시작하는 값도 수식으로 실행되지 않게 막는다.

**코드 검증 결과 (2026-11-26, 합성 이벤트로 탐지기·사건 묶음 시험, 실환경 아님)**
- 1번(3회 의심·5회 차단), 3번(ERP가 비인가 IP 거부), 4번(자동 잠금 10분 후 수동 해제): 코드와 일치.
- 2번(같은 공격으로 보기): 처음에는 사건이 2개로 갈라졌다. `incident_service.py`에서 같은 실패 기록의 "의심" 경보(3회 연속, 여러 계정)를 차단 후보 사건에 합치도록 수정했다. 근거 기록은 늘리지 않아 승인 조건은 그대로다. 시험: `tests/test_incident_merge.py`.
- 로그인 실패 그래프·시간당 요약은 5번째 실패(ERP가 잠금으로 거부한 시도)도 실패로 센다. 입력 형식 오류(400)는 그래프에서 제외한다.
- 아직 안 한 것: 실제 ERP에서 계정이 두 IP에 걸쳐 5회 실패했을 때 잠금 사건이 나오는지(6번 실환경 시험에서 확인). 임시 IP 승인 시간(현재 5분)은 따로 확정하지 않았다.

## 5. 해제와 복구

- 계정 잠금 해제: 대시보드 사건 상세에서 담당자가 사유와 함께 해제 → ERP에 `account_unlocked` 기록.
- 임시 IP 승인·권한 부여: 만료 시각이 지나면 자동으로 끝난다. 연장은 새로 승인해야 한다.
- 모든 조치는 누가·언제·왜 했는지 기록한다(`operator`, `reason`).
