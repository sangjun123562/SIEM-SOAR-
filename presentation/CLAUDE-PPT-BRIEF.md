# Sentinel 캡스톤 최종 발표 · Claude 제작 브리프

## 1. 범위와 우선순위

실제 SIEM·SOAR 통합 보안관제 시스템의 **설계·구축, 공격 탐지와 보안 조치, 동작과 안전성 검증**을 보여준다. 청중은 가상의 회사에서 한 사건이 발생해 증거가 모이고, 담당자의 승인으로 대응하며, 접속을 다시 확인하는 과정을 따라간다. Toolkit은 발표 범위에서 제외한다. 프로젝트 소스, 설정, 사용자 첨부 원본은 읽기 전용이다.

이 브리프는 발표 구조·시간·제작 순서의 최신 기준이다. 시각 제작에는 `presentation/DESIGN.md`를 함께 적용한다. `presentation/guidelines-v2/`는 이전 기술 조사·내용 참고 자료로 보존한다. 이전 15장, 8분 45초, 순차 5장 제작 계획에 우선하여 아래의 **12장·시연 포함 10분·대표 5장 승인 절차**를 적용한다. 이전 `output/design-review.md`는 과거 시안의 검수 기록이다.

## 2. 시간과 결과물

- 본편 12장, 16:9, 편집 가능한 PPTX와 한국어 발표자 노트.
- 슬라이드 배정 합계 **7분 25초**. 시연 영상 **약 2분**, 전환·마무리 **약 30초**로 총 **9분 55초**. 30초 안에 영상 전환과 영상 후 마무리 한 문장을 포함한다. 실측 영상 길이와 첫 리허설 결과를 확인한 뒤 10분 이내로 조정한다. 예상 발표 시간을 실제 리허설 결과처럼 표현하지 않는다.
- 질의응답용 부록은 본편 시간에 포함하지 않는다. 질의응답까지 제한 시간에 포함되는지 확인이 필요하면 확인 사항에 적는다.
- 최종 제출은 승인 이후 편집 가능한 PPTX, 장별 PNG, 발표자 노트, 부록, 검수 결과로 구성한다.

## 3. 제작 순서와 승인

1. 이 브리프와 `presentation/DESIGN.md`를 먼저 읽는다. 참조 이미지 `presentation/references/design/selected-14-scene-reference.png`의 14개 독립 장면을 왼쪽→오른쪽, 위→아래 순서로 읽는다. 14개는 시각 레퍼런스이고 본편 장수는 12장이다.
2. 읽기 전용으로 발표 기준 SHA, 최신 구현, 실제 화면, 시험 기록, 팀 기록과 시연 영상 또는 콘티를 조사한다. 기존 PPT와 노트, v2 교재 3편은 사용자 제공 패키지의 원본으로 참고한다. 접근할 수 없는 원본은 확인 사항에 적는다. `presentation/output/evidence.md`와 `missing-assets.md`는 재확인의 출발점으로 사용한다.
3. **첫 제출은 전체 발표·디자인 설계안**이다. `presentation/output/claude-plan/`에 12장별 핵심 메시지, 다음 장으로 이어지는 한 문장, 자료·근거, 화면의 첫 시선, 도형 역할, 발표 시간과 영상 전환 계획을 남긴다. 미확인 자료와 사실을 함께 표시한다. 이 단계에서 PPT 본편을 생성하지 않는다.
4. 설계 검토 후 **01 표지, 03 팀원 및 제작 과정, 05 전체 아키텍처, 07 제품 화면, 10 안전장치 및 검증 결과**만 편집 가능한 대표 PPT로 제작한다. 원래 본편 번호를 기록한다. 실제 PPT 제작 도구를 사용하고, 각 장 PNG·모아보기·검수 기록과 함께 `presentation/output/claude-pilot/`에 제출한다.
5. 대표 5장 **디자인 승인 후** 전체 12장과 부록을 제작한다. `presentation/output/claude-final/`에 최종 PPTX, PNG, 검수 결과를 저장하고 실제 발표 환경에서 시간과 영상 재생을 확인한다. 승인 여부와 미확인 기술 근거가 남으면 기록한다.

## 4. 슬라이드별 설계

| 장 | 시간 | 역할과 구성 |
| --- | ---: | --- |
| **01 표지** | 20초 | **SIEM·SOAR 기반 통합 보안관제 시스템**. 부제 **From Detection to Response / 탐지에서 대응, 그리고 복구까지**. 제목과 대표 그래픽 하나가 중심. 네트워크 경계·이벤트의 연결을 추상화하고, 검증된 발표 메타데이터만 넣는다. |
| **02 목차** | 10초 | **Introduction → Engineering → Security Operations → Validation**. 발표의 네 구간을 한눈에 보여준다. 메뉴나 세부 기능을 읽는 장으로 만들지 않는다. |
| **03 팀원 및 제작 과정** | 30초 | 확인한 팀원명·분담·개발 기간·실제 산출물. 각자 역할이 보이는 소품과 동작을 넣은 동일 그림체의 작은 캐릭터로 유머를 한 번 사용한다. 예시 문구는 “가상의 회사 하나를 만들고, 직접 괴롭혀 보고, 다시 지켰습니다.”라고 둘 수 있다. 사진을 임의로 만들거나 개인 성과·기간을 추정하지 않는다. |
| **04 프로젝트 개요 및 개발 목적** | 40초 | 로그 분산과 개별 분석의 한계 → 탐지와 조치 사이의 단절 → 가상 기업·통합 분석·조사·실제 조치와 복구를 연결. 차별점은 격리 시험망의 통신과 ERP 계정·권한을 실제로 제어할 수 있는 설계다. |
| **05 전체 시스템 아키텍처** | 60초 | 시험망·SOC·공유 로그·조치망을 영역 기반으로 그린다. 단말 A/B/X, Gateway, Caddy/WAF, ERP/ERP DB, 공유 로그 볼륨, Collector, SOC PostgreSQL, Sentinel Dashboard, 선택 실행 Grafana, 조치망과 ERP 제어망을 확인해 반영한다. 업무·로그·조치의 세 종류 연결을 분명히 한다. 기술 이름과 사용 이유는 해당 노드와 노트에 붙이고 별도 로고 나열 장을 만들지 않는다. |
| **06 시스템 동작 및 데이터 흐름** | 35초 | ERP 사용자 행동 → Gateway·Caddy·ERP 로그 → 수집·정규화 → 이상행위 탐지·경보 → 사건 → 담당자 확인·대응. ERP/Caddy는 요청 ID로 정확히 연결하고, Gateway는 시간·통신 정보로 관련 후보를 연결한다. 인포그래픽으로 데이터의 변환을 보여준다. |
| **07 Sentinel 관제 대시보드** | 50초 | 실제 제품 전체 화면을 크게 두고 관찰→확대→판단 순서로 보여준다. 현황→사건 선택→근거→승인·해제가 주요 흐름이다. 이벤트·보고서·로그 소스·계정 및 권한 메뉴는 실제 구현을 확인해 노트 또는 부록으로 보완한다. |
| **08 보안 프레임워크 및 설계 레퍼런스** | 25초 | 확인된 범위에서 ATT&CK의 공격 분류·탐지 설계 참고, Wazuh의 관제·이벤트 분석 참고, 자체 Sentinel 구현의 대응 관계를 짚는다. 기술 ID는 매핑 근거가 있을 때만 기재한다. 비교 시험이나 참고 기록은 엔진 통합과 구별한다. |
| **09 공격 유형별 탐지 및 방어** | 65초 | 대표 인증 실패 사례는 최신 코드로 확인한 시간 창·횟수·계정·IP 기준을 시간축에 표시한다. 반복 실패, 다중 계정/출발지, 비인가 IP, 문서 권한 위반, WAF 검사를 유형별로 묶고 실제 대응 가능 여부를 표시한다. 접근통제·ERP 자동 잠금·WAF·SIEM 탐지·사람 승인 IP 차단을 구별한다. |
| **10 보안 안전장치 및 검증 결과** | 50초 | 시험 단말 A의 차단과 복구, 대조 단말 B의 정상 유지가 시각 중심이다. 시험 수치 세 개와 날짜·환경·커밋은 보조 증거로 붙인다. 안전장치는 실시간/신뢰, 권한/승인, 대상·기간·중복, 적용 확인·해제로 묶고 자세한 조건은 노트나 부록으로 보낸다. |
| **11 한계점 및 향후 개선** | 40초 | 확인된 한계와 개선 방법을 짝짓는다. 실습망 범위, 라벨 기반 오탐·미탐 평가, 로그 부하와 운영 확장, 대응 정책 중 실제로 설명할 수 있는 2–3개를 선택한다. 구현된 기능을 미구현으로 묘사하지 않는다. |
| **12 결론 및 시연 영상 연결** | 20초 | “흩어진 보안 기록을 연결하고, 탐지 결과를 실제 대응과 복구로 이어지는 시스템을 구축했습니다.” 다음 영상에서 볼 항목을 한 문장으로 제시한다. 영상은 약 2분이며 사건 발견→근거→승인→대상 차단→해제·복구의 실제 동작을 보여준다. 영상 재생 뒤 전환 여유에서 핵심 성과 한 문장으로 마친다. |

## 5. 근거와 범위 검증

- 발표 기준 브랜치·커밋과 확인일을 먼저 확정한다. 앞선 조사 기준은 원격 main `d55e510`이다. 현재 소스·런타임 캡처·과거 시험은 각각의 기준을 표시한다. 자동 pull, 소스 수정, 방화벽 변경, DB 초기화, 배포를 하지 않는다.
- 자료 우선순위는 최신 코드·설정과 실제 시험 원본 → 같은 버전의 설계·기록 → 시연 화면·영상 → 기존 PPT·노트와 가이드 세 편이다. 기존 프로젝트 이해, Docker Compose 이해, 탐지·대응 함수 이해 가이드 v2는 역사 자료다.
- 아키텍처는 Compose, 네트워크 설계, Caddy 설정, 로그 계약을 대조한다. A/B/X 중 X의 선택 실행 여부와 접근 정책, Grafana의 선택 실행 여부를 확인한다. 기술 스택의 실제 역할과 선택 이유를 구분한다.
- 사건 화면은 동일 사건 ID를 기준으로 선택 행·상세 이벤트·IP·시간을 맞춘다. 요청 ID가 보이지 않으면 확인 범위만 밝힌다. 화면의 시연 계정·주소와 민감 정보 공개 범위를 점검한다. 캡처 일자·환경·확인 가능한 버전을 남긴다.
- WAF 기본 모드, 검사 위치, 로그 경로는 코드로 확인한다. 실차단 성과는 WAF 기록과 ERP 전달 여부 등 실제 실행 증거 확보 후만 쓴다. HTTP 403 단독으로 판정하지 않는다. ATT&CK 기술 ID와 Wazuh 활용 범위는 저장소 근거를 찾고, 외부 자료 참고가 필요하면 정확한 공식 출처를 인용한다.
- 기존 통합 시험은 `testbed/DAY10_STATUS.md`의 **2026-11-20 A PC, `abb755f`, 3회 × 회차당 20개 점검, 실패 0**이다. 인증된 승인 경로를 자동화 스크립트로 호출했다. 같은 사건의 실시간 시연, 최신 발표 버전 재시험, 별개의 60종 시험으로 표현하지 않는다. A/B 비교와 해제 후 HTTPS 접속을 근거와 대조한다.
- 미확인 팀 정보, 실제 구현 범위, 실행 버전, 최신 시험, 영상 파일은 확인 목록으로 남긴다. 발표자 노트에는 각 장의 시간·한국어 대본·다음 장 전환 문장·출처·버전을 기재한다.

## 6. 부록과 제출 검수

- 부록 후보는 Compose/네트워크 상세, 기술 스택 선택 근거, 전체 탐지 규칙과 확인된 ATT&CK 매핑, 접근통제 정책, WAF 설정·시험, DB 관계, 주요 함수, 대시보드 메뉴, 통합 시험과 안전장치다. 근거가 없는 장은 비워 둔다.
- PNG를 발표 크기와 축소판으로 검수한다. 첫 시선, 한글 폰트, 여백, 잘림, 겹침, 실제 도식 연결, 캡처 확대, 결과 범위 혼동 여부를 본다. 발견한 문제는 수정 후 다시 렌더링한다.
- 최종 제출 전 발표자 노트와 영상까지 이어 읽어 10분 이내인지 확인한다. 영상이 준비되지 않았다면 영상 구성안과 확보 상태를 각각 명시한다.
