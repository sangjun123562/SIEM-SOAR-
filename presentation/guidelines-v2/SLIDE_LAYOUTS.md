# SLIDE_LAYOUTS.md — 슬라이드별 배치 설계 v2

`CONTENT.md`의 본편 15장을 기준으로 한다. 아래는 레퍼런스 선정 전의 상세 와이어프레임이며, 승인된 레퍼런스에 따라 디자인 토큰과 배치를 조정할 수 있다. 슬라이드 사실과 발표 목적은 유지한다. 좌표는 13.333 × 7.5in 화면의 대략적인 영역(좌측 상단 x=0,y=0)을 설명하며, 실제 요소가 넘치면 그리드 내에서 재배치한다. 레퍼런스와 수치를 기계적으로 맞추지 말고 렌더링 후 검수한다.

## 대표 4장 — 본편 01, 04, 10, 13

### 01. 표지 / 브랜드형 타이포그래피

```text
┌──────────────────────────────────────────────────────┐
│ SIEM · SOAR CAPSTONE                                 │
│                                                      │
│ 통합보안관제 시스템               [기술 연결 모티프] │
│                                  업무 ─ 관제 ─ 대응 │
│ 탐지에서 승인 기반 대응까지        절제된 벡터 그래픽 │
│                                                      │
│ 팀·과정·발표자·날짜                                  │
└──────────────────────────────────────────────────────┘
```

- 배경 Night 또는 승인된 밝은 레퍼런스. 제목 x=.75~7.6, y=1.7~4.2, 48–60pt. 짧은 부제와 메타데이터는 크기 대비를 준다.
- 우측 4~5열에 네트워크 경계·증거·제어선을 추상화한 자체 그래픽. 실제 아키텍처를 주장하는 그림은 아니며, 의미 없는 신경망/방패/네온으로 채우지 않는다. 여백이 주인공이 되지 않게 제목과 그래픽의 균형을 맞춘다.
- 팀명·이름·날짜 확인 후 표기. 질문형 도입은 02장으로 넘긴다.
- 승인 체크: 1초에 프로젝트 주제가 읽히는가? 실제 브랜드처럼 보이되 타사 로고를 복제하지 않는가?

### 04. 전체 시스템 아키텍처 / 영역형 구조도

```text
┌──────────────────────────────────────────────────────┐
│ 업무·수집·조치 경로를 분리했다                       │
│                                                      │
│ Host   ┌─ 시험망 / 업무 통신 ─────────────────────┐  │
│ 중계 → │ 단말 → GATEWAY → Caddy / WAF → ERP → DB │  │
│        └─────────┬──────────┬───────────┬─────────┘  │
│                  └─ 로그 저장소 (볼륨) ─┘            │
│                              ┊ 읽기 전용            │
│        ┌─ SOC 관제 영역 ────▼─────────────────────┐  │
│        │ COLLECTOR → SOC DB → DASHBOARD  Grafana  │  │
│        └─────────────────────────┬────────────────┘  │
│                                  └─ 제어망 → GW/ERP │
│ 범례: 업무 실선 / 로그 점선 / 보안 조치 실선         │
└──────────────────────────────────────────────────────┘
```

위 ASCII는 논리 배치의 개념이며 최종 도식의 정확한 연결은 코드 검증 후 작성한다. 특히 Grafana의 DB 조회선과 Dashboard의 두 조치선은 실제 도착 노드까지 그린다.

- 상단 제목 y=.45~1.25, 도식 x=.75~12.6, y=1.55~6.6(본문 대부분). 의미 없는 긴 부제는 생략하거나 도식 근거를 한 줄로.
- 상단 시험망과 하단 SOC 영역의 경계를 서로 다른 저채도 면 또는 라벨로 분리. 단말망/서버망 경계도 필요에 따라 간결히 표시. 외부 브라우저 중계는 영역 밖에 배치한다.
- 핵심 서비스(Gateway, Collector, Dashboard)는 더 넓은 모듈이나 제목 대비로 강조. 나머지 서비스는 더 작은 보조 라벨. DB는 저장소 형태, 볼륨은 공유 저장소 형태로 표현. 모든 서비스가 동일 크기 흰 사각형인 현재 시안을 반복하지 않는다.
- 업무 경로의 실선, 로그 볼륨의 점선, 조치 경로의 색 실선을 실제 도식 안에서 사용한다. 제어망을 하단 문장만으로 처리하지 않는다. 겹치는 선을 줄이기 위해 오른쪽 또는 왼쪽 외곽의 되돌아가는 경로를 사용한다.
- WAF 엔진, 배치, 수집 경로와 Grafana 선택 실행 여부는 발표 기준 코드에서 확인. 7개 망과 모든 IP는 부록 A1. 로그 공유와 네트워크 송신을 구별한다.
- 승인 체크: 전체 시스템을 한눈에 볼 수 있는가? 세 경로를 손으로 따라갈 수 있는가? 핵심 요소의 위계가 있는가? 실제 연결을 과장하지 않았는가?

### 10. 관제 대시보드 / 제품 쇼케이스

```text
┌──────────────────────────────────────────────────────┐
│ 사건에서 원본 판단 근거까지 추적한다                 │
│                                                      │
│ ┌──────── 실제 전체 Sentinel 화면 ────────┐  01     │
│ │                                         │  사건   │
│ │  [강조한 실제 행] ────────────────────┐ │  선택   │
│ │                                       │ │         │
│ │                                       └─┼→ [확대] │
│ │                                         │  02     │
│ └─────────────────────────────────────────┘  근거   │
│ 화면 캡처 환경/날짜          실패 · trusted · live  │
└──────────────────────────────────────────────────────┘
```

- 전체 화면 x=.7~8.7, y=1.6~6.65, 약 8열. 화면 비율에 따라 x 폭 조정. 우측 4열은 실제 확대 인셋 및 핵심 설명. 현재 시안보다 스크린샷 중심성이 높아야 한다. 어두운 배경 선택 시 캡처와 배경의 경계를 명확히 한다.
- 원본의 실제 확대 위치를 표시하고 우측 확대와 이어 준다. 원본 화면은 위치 맥락, 확대 화면은 읽을 증거라는 역할 분리. 헤더 문장과 우측 설명의 중복을 삭제한다.
- 스크린샷의 사건 ID·IP·계정·규칙·시간·수집 모드가 서로 일치하는지 확인. 서로 다른 사건이면 '별도 사례'라고 분리. 현재 사용자 제공 시안의 전체 화면은 다중 계정 사건을 선택한 것으로 표시되지만 확대 근거가 그 사건인지 새로 검증해야 한다.
- 기존 assets에 없는 최신 전체 화면 또는 사건 상세는 사용자에게 요청. 저해상도 이미지를 과도하게 확대하거나 AI로 복원·합성하지 않는다.
- 승인 체크: 제품이 중심인가? 원본과 확대가 실제로 연결되는가? 발표 거리에서 적어도 핵심 증거가 읽히는가?

### 13. 검증 결과 / 상태 비교 중심

```text
┌──────────────────────────────────────────────────────┐
│ 대상 단말만 차단하고, 해제 후 접속을 복구했다        │
│                                                      │
│  0 건 실패              3회 반복 × 회차당 20개 항목 │
│                                                      │
│                  차단 전        차단 중       해제 후│
│  시험 단말 A   ● 정상 ──── ■ 차단 ──── ● 복구     │
│  대조 단말 B   ● 정상 ──── ● 정상 ──── ● 정상     │
│                                                      │
│        [실제 시험 출력 또는 짧은 검증 근거]          │
│ 시험 날짜 · PC · 커밋 · 기록 경로                    │
└──────────────────────────────────────────────────────┘
```

- 한 가지 핵심 수치를 주인공으로 하고 나머지 두 수치를 시험 범위로 연결한다. 0건 실패만 대형으로 쓸 경우 반드시 '검증 항목 실패'라는 라벨과 범위를 인접 표시. 상태 비교 자체를 더 강하게 표현하는 레퍼런스라면 수치는 보조로 내려도 된다.
- x=.75~12.5, y=3.0~5.75에 A/B 2줄의 동기화된 시간축 또는 상태 매트릭스. 차단 중 A만 의미 있는 붉은 영역, B는 정상 유지, 해제 후 A는 복구 색. 상태명을 반드시 텍스트로 병기. 장식적인 3개 동일 KPI 카드 금지.
- 시험 기록 `2026-11-20 / A PC / abb755f / 3회 × 20개 / fail=0`을 실제 원본과 대조 후 사용. 과거 결과임을 유지. 새로운 실행 확인을 주장하지 않는다. 실제 시험 출력이 없으면 출처를 표기하고 가짜 터미널 캡처를 만들지 않는다.
- 승인 체크: A만 차단되고 B는 정상 유지한다는 사실이 첫눈에 보이는가? 시험 범위·날짜·커밋이 읽히는가? 60종 테스트 또는 최신 버전 성공으로 오해하지 않는가?

## 부록 설계

A1~A9는 CONTENT.md의 상세 범위를 유지한다. 기술 표는 질문에 직접 답할 수 있도록 제목을 명확하게 지정하고, 전체 IP/규칙 ID/실제 API 상태/테스트 출처를 빠짐없이 읽을 수 있게 배치한다. 본편에 포함되지 않은 복잡한 네트워크와 함수 조건을 부록에서 보완한다. 빈 자료나 미검증 결과로 부록을 채우지 않는다.

## 제작 결과 제출 포맷

- 대표 4장 PPTX + 각 장 PNG + 4장 모아보기. 본편 슬라이드 번호와 pilot 번호 매핑 기록.
- 각 장마다 레퍼런스 파일과 추출 원리, 적용한 구도, 기존 시안과 달라진 점, 실제 확인 근거, 남은 문제가 무엇인지 기록.
- 사용자 승인 후 본편 제작. 최종 렌더에서 누락, 흐름 오류, 읽히지 않는 화면, 시각 중심이 없는 페이지는 수정 후 재검수한다.
