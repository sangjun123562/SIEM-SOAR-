아래의 제목과 시간은 초안이다. 기술 확인 후 사실과 메시지를 유지하는 범위에서 조정할 수 있다. 각 장은 DESIGN.md의 디자인 원칙과 SLIDE_LAYOUTS.md의 상세 배치 지침을 함께 따른다. ART_DIRECTION.md에서 선택한 레퍼런스를 기반으로 표현을 조정한다. 기존 시안은 디자인 개선 대상이며 최신 기능 증거로 취급하지 않는다.

### 01 · 표지 (20초 / A)
- 제목: 통합보안관제 시스템 — SIEM · SOAR
- 부제: 가상 기업의 이상행위 탐지에서 승인 기반 대응 및 복구까지.
- 실제 팀명·발표자·과정명·날짜는 확인 후 입력.
- 설명: 무엇을 만들었는지 한 문장. 문제 제기 질문은 다음 장으로 넘긴다.

### 02 · 문제 정의와 차별점 (35초 / B)
- 제목: 비밀번호를 다섯 번 틀렸다고 단말을 바로 막아도 될까?
- 메시지: 흩어진 로그만으로는 조치 근거를 판단하기 어렵고, 무조건적인 차단은 정상 업무에 영향을 준다.
- 시각: 로그 분산 → 근거 기반 관제 → 제한된 조치와 복구. 기존 프로젝트의 실증 흐름을 차별점으로 제시(시장 최초·상용 제품 대비 우월 주장 금지).
- SIEM은 발견, SOAR는 대응 연결이라는 쉬운 정의를 이 장 또는 발표자 노트에 포함.

### 03 · 팀 구성과 역할 (25초 / B)
- 제목: 시험망, 관제, 보안 정책을 분담하고 통합했다.
- 시각: A/B/C 역할 3열 또는 업무 분담 흐름. 담당자/구현 항목/통합 기여 1줄씩.
- 증거: 팀 문서, PR, 커밋, 통합 시험 기록. 확인 전에는 `담당자 확인 필요` 표시.

### 04 · 전체 아키텍처 (55초 / C)
- 제목: 업무 통신, 로그 수집, 보안 조치의 경로를 분리했다.
- 핵심: 브라우저 중계 → 시험 단말 A/B/(X) → Gateway → Caddy → ERP → ERP DB. 별도 SOC Collector → SOC DB → Dashboard/Grafana. 로그 볼륨 공유(읽기 전용), 조치망 및 ERP 제어망을 별도 흐름으로 그림.
- WAF 위치와 로그 경로는 확인 후 추가. 선택 서비스와 보조 컨테이너는 부록으로.
- 시험망과 관제망을 분리해도 로그와 조치 API가 연결되는 이유를 설명.

### 05 · 기술 스택과 선택 이유 (35초 / B)
- 제목: 실제 통신과 보안 조치를 재현할 수 있는 환경을 선택했다.
- 기술 예시: Docker Compose(재현 가능한 여러 서비스), Macvlan/분리망(독립 단말과 통제 경로), Linux iptables(실제 통신 제어), Caddy(HTTPS 및 요청 전달), Flask/Python(업무 API와 수집·탐지), PostgreSQL(관계형 증거/업무 데이터), Grafana(관제 통계), Node.js(브라우저 중계).
- 구현 확인 후 사용. 기술별 선택 이유는 설계 문서나 팀 판단과 대조하고, 대안을 부당하게 열등하다고 표현하지 않는다.
- 로고 나열 대신 계층별 기술과 목적을 대응시킨다.

### 06 · ERP 접근통제 (45초 / D)
- 제목: 로그인했다고 모든 문서를 볼 수 있는 것은 아니다.
- 실제 ERP 전체 화면 + 권한에 따른 문서 열람 비교. 인증/인가 차이, 출발지 정책, 부서·직급·문서 등급, 임시 권한의 핵심을 설명.
- 계정 잠금, 세션 버전 무효화, 퇴사 계정 권한 회수·복구 등은 최신 구현을 확인하고 노트/부록에서 연결.
- 테스트 계정, 사내 문서는 시연용임을 명시.

### 07 · 로그 수집과 상관분석 (40초 / E)
- 제목: 한 번의 업무 요청을 여러 관점에서 기록한다.
- 시각: Gateway(통신) / Caddy(웹 응답) / ERP(인증·권한) → 공유 볼륨 → Collector·정규화 → SOC DB → 이벤트·경보·사건.
- Caddy/ERP `request_id` 정확 연결 vs Gateway IP·포트·시각 기반 후보 연결. WAF 로그는 실제 확인된 구조에만 추가.
- 가능하면 동일 요청의 실제 마스킹된 로그 예시를 1건 제시한다.

### 08 · 탐지 규칙 (50초 / E)
- 제목: 실패 횟수뿐 아니라 시간과 계정, 출발지를 함께 분석한다.
- 시각: 대표 규칙(같은 계정·IP, 5분 안 실패 5회) 타임라인 + 전체 규칙군 개요.
- 414c49e 기준 교재에는 10개 탐지 유형 / 9개 함수: 3회 관찰, 동일 계정·IP 5회, 동일 IP 다중 계정 합산 5회, 자동 잠금 로그, 다중 계정, 다중 출발지, 실패 후 성공, 다른 IP 성공, 비인가 출발지, 문서 열람 실패. 최신 목록·ID·위험 등급·임계값은 재확인.

### 09 · WAF (40초 / D 또는 E)
- 제목 예시(검증 후 확정): 웹 요청 단계의 공격 패턴까지 관찰한다.
- 실제 사용 엔진/정책, 요청 검사 위치, 탐지 모드와 차단 모드, 로그 및 SOC 연계 여부를 코드로 확인.
- 기존 로그인 API 공격 패턴 테스트의 실제 요청/응답/로그를 확보한 경우에만 검증 결과로 제시. 로컬 격리 환경에서 승인된 테스트만 사용. 실제 차단을 주장하려면 WAF 차단 로그와 ERP 전달 여부를 함께 확인.
- 미구현 또는 검증 미완료라면 `현재 확인 범위 및 향후 과제`로 표현하고 본편 배치를 조정. 임의의 제품명·룰 ID·HTTP 결과를 채워 넣지 않는다.

### 11 · 대응 흐름 및 담당자 권한 (50초 / E)
- 제목: 사건을 발견해도 IP 차단은 담당자의 승인 이후 진행한다.
- 시각: Dashboard 담당자 → 권한·사건 검사 → 승인 선저장 → 조치 API → Gateway 실제 규칙 → 결과 조회.
- 분석가/승인자/관리자 역할(최신 코드 확인), 인증·CSRF·권한 확인, 제한된 대상 및 기간.
- ERP 계정·권한 조치 경로는 Gateway IP 차단과 구분. 계정 자동 잠금도 별도.

### 12 · 안전장치와 복구 (35초 / E)
- 제목: 잘못된 차단을 줄이고, 조치가 실제로 반영됐는지 확인한다.
- live/replay/synthetic 구분, trusted 확인, 허용 규칙·대상, 최대 기간, 중복 조치 방지, 응답 손실 시 unknown과 상태 조회, 수동 해제·자동 만료.
- 이전 교재 기준 IP 차단 최대 30분, A/B만 허용; ERP 계정 잠금 10분은 자동 정책. 최신 값 확인.
- 승인 기록과 적용 상태, 방화벽 규칙 존재와 실제 통신, 해제와 사건 종료는 각각 다르다.

### 13 · 통합 시험 및 성과 (50초 / F)
- 제목: 대상 단말만 차단하고, 해제 후 접속을 복구했다.
- 실제 근거가 확인된 경우: 3회 연속, 회차당 20개 항목, 실패 0(2026-11-20 A PC / abb755f). 또는 별도로 확인한 더 최신 시험 결과를 사용하고 버전을 명시.
- 비교표: A는 정상→차단→복구, B는 정상→정상→정상. 시험 기록과 일치 여부 확인.
- 증거: 실제 로그/시험 출력 또는 시연 녹화의 해당 부분. 과거 실행 결과와 새 발표 버전의 상태를 구분.
- 수치가 없거나 최신 재시험을 못했다면 확인된 과거 기록의 범위를 표시. 탐지 정확도, FP/FN, MTTA/MTTR 등 측정하지 않은 수치를 넣지 않는다.

### 14 · 한계점과 향후 개선 (40초 / B)
- 제목: 시험망에서 검증했고, 실운영 수준의 개선은 남아 있다.
- 후보: 격리 실습 환경 범위, 규칙 기반 탐지의 한계, 실제 운영용 개인 인증 및 권한 분리, 라벨링된 데이터 기반 탐지 품질 측정, 증거 보존·백업, 티켓/SLA/운영 지표, 대응 범위 확대.
- 위 항목은 최신 구현 확인 후 실제 미구현/부분 구현/개선 필요 항목 2–3개만 본편에 선택. 구현된 기능을 미구현으로 단정하지 않는다.
- 개선 계획은 우선순위·효과·검증 방법을 짧게 제시. 달성 완료처럼 말하지 않는다.

### 15 · 결론 및 Q&A (30초 / G)
- 제목: 기록에서 근거로, 근거에서 실제 대응으로.
- 핵심: 격리된 가상 기업, 통합 탐지, 안전한 조치, 검증 가능한 복구를 하나의 시스템으로 연결.
- 확인된 성과 1개로 마무리. 질문을 받겠다는 멘트.

## 6. 발표자 노트와 출처 기록

- 모든 본편 슬라이드에 실제로 읽을 수 있는 자연스러운 한국어 대본을 작성한다. 노트 첫 줄에 시간 구간·계획 시간을 표시한다. 슬라이드 문구를 그대로 읽기보다 그림을 가리키며 설명하는 방식.
- 각 기술 주장·수치·화면마다 파일 경로, 커밋, 문서 위치 또는 검증 출력의 위치를 노트에 기록한다. 필요한 출처만 본문 작은 각주로 표기.
- `output/evidence.md`에 `주장 | 근거 파일/행 또는 테스트 기록 | 기준 SHA/날짜 | 확인 상태` 표를 작성한다. 확인 상태는 `코드 확인`, `기존 시험 기록`, `현재 실행 확인`, `미확인` 등으로 구분한다. 현재 실행 확인은 실제 실행했을 때만 사용한다.
- 팀 정보, 실제 전체 화면, WAF 증거, 최신 시험 결과 등 빠진 자료는 `output/missing-assets.md`에 모아 사용자에게 요청한다. 없는 자료로 임의의 결과물을 만들지 않는다.
- 현재 지침의 15장 구성은 기존 10분 덱을 보완하기 위한 제안이다. 발표 제한 시간, 필수 평가 항목, 팀별 분담이 확정되면 그에 맞춰 조정한다.
