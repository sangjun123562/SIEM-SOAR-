# DESIGN.md — SIEM · SOAR 발표 디자인 시스템 v2

> 목표: 깔끔한 문서를 가로로 옮긴 슬라이드가 아니라, 전문 디자이너가 설계한 기술 발표를 만든다. 미니멀리즘은 장식을 제거하는 일이 아니라 중요한 정보를 더 강하게 전달하는 일이다.

## 1. 필수 입력과 적용 우선순위

- `CONTENT.md`: 발표 내용, 최신 코드 검증, 출처, 시간 및 사실의 기준. 디자인보다 사실이 우선이다.
- `ART_DIRECTION.md`: 시각적 콘셉트, 레퍼런스 분석, 표현의 밀도와 리듬.
- `SLIDE_LAYOUTS.md`: 본편 15장의 구체적 배치와 대표 4장의 승인 기준.
- `references/design/`: 사용자가 선택한 긍정적 레퍼런스. `references/anti-patterns/`는 피해야 할 현재 시안이며 디자인 원본으로 사용하지 않는다.
- `references/source/`: 기존 PPT와 학습 교재. 내용 참고 전용이다. 현재 발표 기준 커밋과 다른 기능을 섞지 않는다.
- `assets/`: 실제 화면, 도식, 시험 증거. 없는 실제 자료를 가짜 이미지로 대체하지 않는다.

사용자가 승인한 레퍼런스가 있으면 아래 임시 컬러·폰트·레이아웃의 구체값을 바꿀 수 있다. 단, 사실·가독성·편집성·보안·출처 규칙은 유지한다. 상충할 경우 변경 이유를 `output/design-review.md`에 기록한다. 레퍼런스 미확정 상태에서 최종 덱을 제작하지 않는다. 임시안이 필요하면 별도로 명시하고 대표 슬라이드만 제안한다.

## 2. 디자인의 핵심 원칙

- **시각적 중심:** 한 장에 눈이 먼저 가는 요소 하나를 만든다. 대형 제목, 기술 구조도, 실제 UI, 검증 결과 중 그 장의 증거가 중심이 되게 한다.
- **정보 계층:** 핵심 / 보조 / 근거의 크기·굵기·대비를 다르게 한다. 모든 박스·수치·설명에 같은 무게를 주지 않는다.
- **편집 디자인:** 정렬된 그리드를 유지하되 비대칭 분할, 전체 폭 도식, 대형 화면, 타임라인, 비교 매트릭스 등을 주제별로 선택한다.
- **의미 있는 그래픽:** 컨테이너 경계, 데이터의 변환, 상태 변화, 증거 확대처럼 내용에 기여하는 도형과 강조를 사용한다. 장식이 아니라 구조 자체가 디자인이 된다.
- **시각적 리듬:** 밝은 기술 설명 장과 어두운 표지·제품 쇼케이스·결말을 적절히 교차한다. 모든 장의 제목-부제-가로선-표를 기계적으로 반복하지 않는다.
- **읽기 쉬운 기술 발표:** 전문용어를 남발하지 않는다. 한 장의 메시지와 실제 시각 자료가 먼저 읽히고, 상세 조건은 노트와 부록에서 설명한다.

| Paper | #F7F8FA / #FFFFFF | 기술 설명 및 데이터 슬라이드 |
| Ink | #152131 | 제목, 핵심 수치 |

| SIEM | #275A92 | 수집·정규화·탐지·증거의 의미 |
| SOAR | #16766F | 승인·조치·복구의 의미 |
| Traffic | #526477 | 업무 통신 |
| Denied | #B43E42 | 실제 차단·거부·실패 상태에만 |
| Attention | #956319 | 검토 및 제한 사항에만 |

- 색은 구별할 이유가 있을 때 사용한다. SIEM·SOAR 색은 페이지마다 동일한 의미를 유지한다. 모든 강조를 파랑으로 처리하지 않는다. 어두운 배경에서는 대비를 별도로 조정한다.
- 폰트는 Pretendard 우선, 대체 Noto Sans KR 또는 맑은 고딕. 한글·영문·숫자의 균형과 폰트 대체 여부를 실제 렌더링에서 확인한다. 필요 시 숫자 정렬용 tabular 숫자 또는 고정폭 코드를 제한적으로 사용한다.
- 표지 44–64pt, 결론·핵심 숫자 48–80pt, 일반 제목 30–38pt, 본문 20–24pt, 도식 16–20pt, 각주 12–14pt. 부록 14–16pt 허용. 숫자 단위와 설명을 분리하여 시각적 대비를 만든다. 읽히지 않으면 크기를 더 줄이는 대신 분리한다.
- 12열 기준: 좌우 0.65–0.8in, 안전 상하 여백 0.4in 이상, 열 간격 약 0.2in. 대표 요소는 7–9열 또는 전체 폭을 사용할 수 있다. 제목은 도식과 같은 시작선을 유지한다.
- 본문 영역의 대략 55–80%를 의미 있는 시각 자료에 사용한다(내용별 조정). 의도적으로 비워 둔 여백은 허용하되, 단순한 미완성 배치가 되지 않게 한다.

## 4. 슬라이드 유형과 변주

| 유형 | 레이아웃 원칙 |
|---|---|
| A. Cover | 타이포그래피를 크게, 우측에 시스템 관계를 연상시키는 자체 벡터 그래픽. 배경 장식이 주제보다 강하지 않게. |
| B. Editorial | 비대칭 5:7 또는 4:8, 핵심 문장과 근거 도식. 한 줄 헤더와 단순 리스트 반복 금지. |
| C. Architecture | 전체 폭, 시험망/관제망과 저장소/제어망을 공간적으로 분리. 핵심 제어 지점 강조. |
| D. Product | 실제 화면을 지배적 시각 요소로. 원본과 확대 영역, 실제 근거를 연결. |
| E. Process | 시간축·스윔레인·데이터 전후 변화 중 실제 논리에 적합한 표현을 선택. |
| F. Evidence | 가장 중요한 검증 결과가 중심. 수치와 대상/대조 단말의 전·중·후 상태를 함께 표현. |
| G. Close | 한 문장 결론과 근거 있는 성과, Q&A. |
| H. Appendix | 기술 질문에 대응하는 상세 자료. 표와 도식의 가독성 우선. |

전체 본편에 적어도 5개 구성이 실제로 나타나야 한다. 같은 유형을 재사용하더라도 중심 요소와 비율을 달리한다. 배경을 임의로 계속 바꾸지는 않는다.

## 5. 기술 그래픽의 표현 규칙

- 컨테이너/네트워크/볼륨/DB/API를 같은 박스로 처리하지 않는다. 네트워크는 영역 또는 경계, 서비스는 모듈, 저장소는 저장소 표식, API는 방향 있는 제어선으로 구별한다. 그룹 안의 작은 라벨은 배경보다 가독성이 좋아야 한다.
- 실제 기능/중요도에 따라 Gateway, Collector, Dashboard 등 핵심 요소의 비중을 조절하되, 서비스가 동일 규모의 장비라는 의미를 부여하지 않는다.
- 업무 통신은 회색 실선, 로그 수집은 파랑 점선, 조치는 틸 실선과 화살표. 색 외에도 선 스타일·라벨로 구별. 연결선은 실제 출발점과 도착점에 닿게 하고 교차 최소화. 공유 볼륨을 네트워크 송신처럼 그리지 않는다.
- ERP DB와 SOC DB, 일반 업무망과 제어망을 구별한다. ERP 자체 자동 잠금과 관제 IP 차단도 분리한다. WAF·Caddy의 실제 위치, 로그 공유 여부는 발표 기준 코드로 확인한 뒤 표현한다.
- 정확한 Caddy–ERP request_id와 Gateway 통신 후보 연결을 동일 수준의 증거로 표현하지 않는다.
- 본편은 관계와 설계 의도 중심; 전체 IP 및 7개 망 소속 관계, 규칙 ID, API 상태는 부록으로 분리한다.
- 벡터 기반 도식은 PowerPoint 도형·커넥터 또는 편집 가능한 그룹을 우선한다. SVG는 복잡한 그래픽 자산으로 제한하고 원본 소스도 보관한다. Mermaid는 논리 초안에 사용하며 기본 Mermaid 출력이 최종 디자인이라고 가정하지 않는다.

## 6. 제품 화면과 검증 데이터

- 전체 화면의 위치 맥락과 세부 증거의 확대를 함께 제공한다. 실제 UI를 가짜로 재디자인하지 않고 화면 외곽·콜아웃·확대 위치만 설계한다.
- 스크린샷의 강조는 1–3개 이하로 제한하며 설명이 필요한 증거의 좌표를 원본에 실제 연결한다. 증거 글자가 읽히지 않으면 화면 분할 또는 고해상도 재캡처.
- 같은 사건의 상세라는 표현은 실제 incident ID, 시간, 계정, IP 등 일치 근거를 확인한 경우에만 사용한다. 현재 예시 이미지는 사건 일치 여부가 확인되지 않았다.
- 민감한 로그·계정 식별 정보·토큰·비밀번호는 필요한 범위에서 가린다. 날짜·환경·버전·출처를 남긴다.
- 과거 A PC 시험 기록은 `3회 × 20개 항목`, `실패 0`의 범위 내에서 표현한다. 60은 누적 검증 항목 통과 횟수이지 서로 다른 60종 테스트가 아니다. 시험 커밋과 현재 발표 버전을 구분한다. 실제 측정하지 않은 정확도·운영 지표·시간 단축 수치 금지.

## 7. 금지 및 허용

**금지:** 단순한 동일 크기 박스 나열, 모든 장에서 동일 제목+부제+가로선, 무의미한 회색 배경 사각형, 증거 없이 거대한 KPI, 무관한 스톡 해커·자물쇠·네온, 장식용 3D·과도한 광택·그라데이션, 카드의 남용, 가짜 로고·가짜 제품 UI, 왜곡된 그래프, 타사 로고/브랜드 그대로 차용, 기술 사실 변경, 전체 슬라이드의 이미지 평탄화.

**허용:** 실제 네트워크 경계의 컬러 면, 부분적인 어두운 섹션, 선과 면의 깊이 차이, 의미 있는 기술 아이콘, 얇은 스크린샷 프레임, 확대 인셋, 정교한 벡터 그래픽, 실제 상태를 표현하는 색 대비, 강조 타이포그래피. 각 요소는 설명 목적을 가져야 한다.

## 8. 제작 승인 및 품질 게이트

1. `ART_DIRECTION.md`의 레퍼런스 분석 및 2개 시각 방향을 비교. 승인된 하나를 선택하고 디자인 토큰·규칙을 고정한다.
2. `SLIDE_LAYOUTS.md`의 대표 4장(본편 01,04,10,13)만 제작하고 PNG 렌더링. 번호는 pilot 01~04일 수 있으나 본편 매핑을 기록한다.
3. **디자인 검수와 기술 검수를 별개로 수행한다.** 아래 실패 항목 중 하나라도 있으면 해당 장을 다시 설계한다: 시각 중심 불명확, 모든 요소 무게 동일, 현재 안티패턴과 유사한 단순 박스 나열, 화면 근거 안 읽힘, 실제 도식 연결 불명확, 시험 범위 오해, 화면 겹침·잘림.
4. `output/design-review.md`에 각 대표 장의 시각 중심, 배치 선택 이유, 참조 이미지 및 페이지, 실제 렌더링에서 발견한 문제와 수정 내역을 기록한다. `output/pilot.pptx`, `output/pilot-preview/`, 모아보기 이미지도 제출한다. 승인 전 전체 덱 생성 금지.
5. 승인 후 전체 PPTX를 제작. `CONTENT.md`의 발표 시간 및 기술 근거와 `SLIDE_LAYOUTS.md`의 장별 목적을 유지한다. 원본 자료 및 프로젝트 코드는 읽기 전용, 제작물은 output에만 저장한다.
6. 모든 슬라이드를 100% PNG와 썸네일로 검사하고 폰트, 잘림, 겹침, 연결, 이미지 품질, 발표자 노트 및 출처를 확인한다. 가능하면 실제 발표 PC의 PowerPoint로 최종 확인한다.
7. `output/final.pptx`, `output/preview/`, 가능하면 `output/final.pdf`, `output/verification.md`, `output/evidence.md`, `output/missing-assets.md` 제출. 검증하지 않은 것은 명시한다.
