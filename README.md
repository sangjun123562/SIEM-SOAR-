# Mg · ERP 로그인 탐지 개선

**C 담당인 Mg는 ERP 로그인 기록을 더 정확하게 관제 사건으로 만드는 작업을 맡았습니다.** 여러 계정명이나 IP에 흩어진 실패도 찾고, 입력 오류나 중간 로그인 성공 때문에 별개로 봐야 할 실패가 하나의 사건으로 합쳐지는 경우를 줄였습니다.

[내가 만든 기능](#1-내가-만든-기능) · [적용 후 확인할 결과](#2-적용-후-확인할-결과) · [상세 안내서](Mg_LOGIN_DETECTION_GUIDE_codex.md)

**팀 적용 상태** 여러 계정명·여러 IP의 실패 탐지와 오탐 감소는 [PR #35](https://github.com/sangjun123562/SIEM-SOAR-/pull/35)로 `main`의 `4c1a935`에 들어갔습니다. 실패 3~4회 뒤 성공한 경우의 주의 표시와 **실패·성공 IP가 다른 경우의 추가 표시**는 `Mg`에서 확인할 수 있습니다.

## 1. 내가 만든 기능

### 여러 계정명이나 IP에 흩어진 실패도 찾아냅니다

기존 반복 실패 규칙과 아래 두 추가 규칙은 5분 동안 신뢰된 출발지에서 ERP가 인증을 거부한 기록(`401`)을 확인합니다.

| 규칙 | 언제 사건이 생기나요? | 화면에서 할 수 있는 일 |
| --- | --- | --- |
| 기존 · 같은 계정명과 같은 IP | 한 실패 묶음에서 같은 계정명과 IP로 **5회** 실패 | 근거를 보고, 기존 조건을 충족하면 차단을 승인할 수 있습니다. |
| Mg 추가 · 같은 IP에서 여러 계정명 | 한 IP에서 **서로 다른 계정명 3개**로 실패 | 관련 계정명과 원본 로그를 확인합니다. 조사용입니다. |
| Mg 추가 · 같은 계정명에서 여러 IP | 한 계정명으로 **서로 다른 IP 3곳**에서 실패 | 관련 출발지와 원본 로그를 확인합니다. 조사용입니다. |

**예를 들어** 같은 IP에서 `alice → alice → bob` 순으로 실패하면 계정명은 두 개입니다. 5분 안에 `charlie`가 추가되면 세 개가 되어 조사용 사건이 생깁니다. 두 추가 규칙의 사건에는 **조사용 · 차단 불가**가 표시되며 서버에서도 승인을 거부합니다. [탐지 함수와 한글 주석](src/soc/detector.py#L292)

### 서로 다른 실패 묶음으로 생긴 불필요한 사건을 줄입니다

형식 오류(`400`)는 인증 실패에서 뺍니다. 같은 계정·신뢰된 같은 IP·같은 종류의 수집 기록에서 로그인에 성공하면, 기준에 못 미친 실패를 앞뒤로 나눠 셉니다.

| 같은 합성 로그로 비교한 경우 | 변경 전 → 변경 후 |
| --- | ---: |
| 인증 실패 4회 + 입력 형식 오류 1회 | 사건 **1 → 0** |
| 실패 2회 → 로그인 성공 → 실패 3회 | 사건 **1 → 0** |
| 중간 성공 없이 인증 실패 5회 | 사건 **1 → 1** |
| 인증 실패 5회 → 로그인 성공 | 사건 **1 → 1** |

이미 사건이 생겼다면, 마지막 실패 뒤 5분 안에 조건에 맞는 성공의 **시각과 원본 기록 번호**를 상세에서 보여줍니다. 정상 직원도 성공 전에 실제 인증을 5회 연속 실패하면 사건으로 잡힐 수 있습니다. 담당자는 실패와 성공 기록을 함께 보고 판단합니다. [실패를 묶는 코드](src/soc/detector.py#L118) · [성공 기록 조회](src/soc/repository.py#L167)

### 3~4회 실패 뒤 성공하면 주의 표시를 띄웁니다

같은 계정명·신뢰된 같은 IP·같은 수집 방식에서 **5분 안에 인증 실패 3~4회 뒤 성공**하면 **`주의 · 반복 실패 후 로그인 성공`**이 목록에 표시됩니다. 상세에서 실패·성공 결과, 시각, 출발지, 원본 기록을 확인할 수 있습니다. 정상 직원도 같은 기록을 남길 수 있으므로 담당자가 검토하며, 이 사건은 차단 승인 대상에서 제외됩니다.

| 같은 계정과 출발지의 기록 | 관제 화면 결과 |
| --- | --- |
| 실패 1~2회 → 성공 | 이 규칙의 주의 사건 없음 |
| 실패 3~4회 → 성공 | **주의 사건 1건** |
| 실패 5회 → 성공 | 기존 반복 실패 사건 유지. 같은 실패 묶음의 주의 사건은 추가하지 않음 |

[주의 사건 생성 코드](src/soc/detector.py#L80)

### 실패와 성공의 출발지가 다르면 따로 표시합니다

한 신뢰 IP에서 같은 계정명으로 **실패 3~4회**가 이어지고 **다른 신뢰 IP에서 5분 안에 성공**하면 **`주의 · 반복 실패 후 다른 출발지에서 로그인 성공`**을 표시합니다. 양쪽 기록이 같은 수집 방식이어야 합니다. 상세에서 실패 IP, 성공 IP, 시각, 원본 로그를 확인할 수 있습니다. 직원이 기기나 네트워크를 바꾼 경우도 있으므로 조사용으로 표시하고 차단 승인은 제한합니다. [출발지가 달라진 경우의 탐지 코드](src/soc/detector.py#L238)

## 2. 적용 후 확인할 결과

- [ ] 기존 규칙의 실패 4회에서는 경보가 없고, 5회에서 사건이 생깁니다.
- [ ] 두 추가 규칙은 서로 다른 값이 3개가 되면 사건이 생기고, 같은 기록을 다시 처리해도 사건이 중복되지 않습니다.
- [ ] 조사용 사건에서는 계정명·출발지·원본 로그를 볼 수 있고, 화면과 서버에서 차단 승인이 제한됩니다.
- [ ] 실패 5회 뒤의 성공이 상세에 표시되며, 기존 승인·해제 흐름도 동작합니다.
- [ ] `Mg`의 새 주의 규칙에서 실패 3~4회 뒤 성공이 목록에 표시되고, 실패·성공 원본을 확인할 수 있습니다. 같은 기록을 다시 처리해도 주의 사건은 1건입니다.
- [ ] 같은 계정이 다른 신뢰 IP에서 성공한 경우에는 **주의 · 실패와 성공의 출발지가 다름**이 표시되고, 상세에서 두 IP를 모두 확인할 수 있습니다.

**확인한 범위** 로컬 `Mg` 테스트 **44개 통과, PostgreSQL 연동 1개 건너뜀**입니다. 팀 Docker·PostgreSQL 환경에서 실제 화면과 저장 결과를 확인하는 단계가 남아 있습니다. [팀 환경 검증 체크리스트](Mg_LOGIN_DETECTION_GUIDE_codex.md#5-적용-후-검증-체크리스트)

## 3. C 담당 진행 상황

| 작업 | 상태 |
| --- | --- |
| 1. 찾는 규칙이 1개뿐 | **구현·로컬 검증 완료** · 조사용 규칙 두 개 추가 |
| 2. 정상 직원도 사건이 될 수 있음 | **구현·로컬 검증 완료** · 불필요한 사건 감소. 팀 검토에서 나온 3~4회 실패 뒤 성공의 주의 표시를 3번에 반영 |
| 3. 놓치는 로그인 실패 패턴이 있음 | **진행 중** · 실패 3~4회 뒤 같은 IP 성공에 이어, 다른 IP 성공도 로컬에서 검증 |
| 4. 수집기 재시작 중 기록 분류 | **대기** · 수집 중단 중 기록과 재시작 뒤 새 기록의 구분 기준 확인 예정 |
