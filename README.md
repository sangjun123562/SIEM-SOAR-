## 탐지 규칙 3개 (기존 1개 + Mg가 추가한 2개)

세 규칙 모두 **최근 5분** 안의 신뢰된 출발지에서 ERP가 인증을 거부한 기록(`401`)을 봅니다.

| 규칙 | 이런 경우 사건이 생깁니다 | 의심 상황 | 코드 위치 |
| --- | --- | --- | --- |
| 기존 · 같은 계정 + 같은 IP | 같은 조합이 한 실패 묶음에서 **5번** 실패 | 한 계정의 반복 인증 실패 | [`detect_login_failures()`](src/soc/detector.py#L77) |
| 🆕 **추가 1 · 같은 IP + 여러 계정명** | IP 하나에서 **서로 다른 계정명 3개**가 실패 | 여러 계정명에 걸친 인증 실패 | [`detect_multi_account_failures()`](src/soc/detector.py#L177) |
| 🆕 **추가 2 · 같은 계정명 + 여러 IP** | 계정명 하나가 **서로 다른 IP 3곳**에서 실패 | 한 계정명에 모인 여러 출발지의 실패 | [`detect_multi_source_failures()`](src/soc/detector.py#L186) |

### 예시: 추가 1은 이렇게 셉니다

같은 IP에서 아래 순서로 로그인 실패가 들어왔다고 해 보겠습니다.

| 시각 | 실패한 계정명 | 서로 다른 계정명 | 결과 |
| --- | --- | --- | --- |
| 09:00 | alice | alice → **1개** | 대기 |
| 09:01 | alice | alice → **1개** (같은 이름은 다시 세지 않음) | 대기 |
| 09:02 | bob | alice, bob → **2개** | 대기 |
| 09:04 | charlie | alice, bob, charlie → **3개** | 🚨 **사건 생성** |

추가 2는 "계정명" 자리에 "IP"를 넣어 똑같이 셉니다.

### 새 사건은 "조사용"입니다

추가 규칙은 공유 IP를 쓰는 사무실이나 장소를 옮겨 다니는 직원처럼 **정상적인 사용에서도** 생길 수 있습니다. 그래서 새 사건은 관제 화면에 **조사용 · 차단 불가**로 표시됩니다. 담당자는 어떤 계정명·IP가 쓰였는지와 원본 로그를 확인합니다. 차단 승인 버튼은 비활성화되고, 누가 요청을 보내더라도 서버가 한 번 더 거부합니다.

## 정상 입력 실수는 어떻게 구분하나요?

입력 양식 오류(`400`)를 실패 횟수에서 뺍니다. 같은 계정·신뢰된 같은 IP·같은 수집 방식에서 기준 이전에 성공하면 앞뒤 실패를 따로 셉니다. 실패 5회로 이미 생긴 사건은 유지하고, 이후 5분 안에 조건에 맞는 첫 성공이 있으면 사건 상세에 시각과 원본 기록 번호를 표시합니다.

| 같은 합성 로그를 비교한 사례 | 사건 수 변경 전 → 변경 후 |
| --- | --- |
| 인증 실패 4회 + 입력 형식 오류 1회 | **1 → 0** |
| 실패 2회 → 로그인 성공 → 실패 3회 | **1 → 0** |
| 중간 성공 없이 인증 실패 5회 또는 실패 5회 뒤 성공 | **각각 1 → 1** |

실제 인증 실패가 성공 전에 5회 연속 발생하면 정상 직원도 사건으로 잡힐 수 있습니다. 담당자는 그 경우 성공 기록을 포함한 근거를 보고 판단합니다.

## 팀원 적용 방법

본인 작업 브랜치에서 변경을 저장하고, 최신 `main`을 반영한 뒤 저장소 루트에서 실행합니다. 아래 패치는 공통 `main`을 제외한 Mg의 코드·테스트 6개 파일 변경만 가져옵니다.

```bash
git status --short --branch
git fetch origin main Mg
git diff origin/main...origin/Mg --output=mg_rules.patch -- src/soc/detector.py src/soc/incident_service.py src/soc/dashboard.py src/soc/repository.py tests/test_detector.py tests/test_day5_live_db_and_auth.py
git apply --3way --check mg_rules.patch
git apply --3way mg_rules.patch
python -B -m unittest discover -s tests -v
```

적용 확인이 실패하거나 같은 기능을 이미 반영했다면 먼저 파일과 이력을 비교하세요. 테스트와 변경 파일을 확인한 뒤 본인 브랜치에서 커밋할 수 있습니다. [명령별 설명과 충돌 확인 방법](Mg_LOGIN_DETECTION_GUIDE_codex.md#5-팀원-적용-방법)

## 적용 후 확인할 결과

- 기존 규칙: 실패 **4번까지는 경보 없음**, **5번째에 경보**가 납니다.
- 추가 규칙: 서로 다른 계정명(또는 IP)이 **3개가 되는 순간** 사건이 생깁니다. 같은 로그를 다시 읽어도 사건이 중복으로 생기지 않습니다.
- 새 사건에서는 차단 버튼이 비활성화되고, 방화벽 차단 요청이 **0건**이어야 합니다.

**Mg 로컬 검증** — `main` `4fb91f8`과 합친 뒤 전체 테스트 **41개 중 40개가 통과**했습니다. PostgreSQL 접속 설정이 필요한 1개는 건너뛰었습니다. 팀 Docker·PostgreSQL 환경에서는 [안내서의 검증 체크리스트](Mg_LOGIN_DETECTION_GUIDE_codex.md#6-적용-후-검증-체크리스트)로 확인하면 됩니다.
